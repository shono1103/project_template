# verify-task

`test/` 配下の手順書を読み、**人が実機を操作して、Claude が指示と判定の選択肢を出す。**
このスキルはブラウザを触らない (Claude が自分で操作するのは run-manual-test の担当)。

手順の実体は `test/<領域>/<機能>/<章>.feature`、タスクとの対応はタスク md の
frontmatter `test:`、結果は `job/<案件名>/task/assets/<タスク名>/<実行日>/`。
記法は [test/README.md](../../../test/README.md) に従う。

**Claude が代わりに判断しないのが肝。** 画面を見ているのは人だけなので、
「たぶん OK だろう」で先に進むと確認したことにならない。
選択肢を出して選んでもらい、選ばれたものだけを結果にする。

## 引数

* **タスク名** — 対象のタスク。部分一致で探し、複数該当したら候補を挙げて確認する。
  省略時は `progress` のタスクから選ばせる (`test:` が空のものは候補に出さない)。
* **シナリオ ID / 章** — `U-1-1` や `U-1` のように指定された場合はそれだけを回す。
  省略時は全シナリオ。**再確認では章単位の指定が多いので、必ず受け付ける。**

## 手順

### 1. 対象を決める

タスクの実体から `test:` を読み、feature の一覧に展開する。
ディレクトリなら `_` で始まらない `.feature` をファイル名順に全部。

```sh
J="job/<案件名>/task"
sed -n '/^---$/,/^---$/p' "$J/list/<タスク名>.md"
ls test/<領域>/<機能>/
```

`test:` が空で、タスク md の本文に Gherkin が埋まっている場合は
**`test/` への抽出を提案して、そこで止まる。** 勝手に移動しない
(どの機能ディレクトリに置くかは人が決めた方がよい)。

`test:` も本文の Gherkin も無ければ、手順書が無いということなので
「手順書を作るところから始めますか」と聞いて終える。

### 2. 前提を確認する

`_background.feature` の `Background:` と、対象の章が持つ独自の `Background:` を提示し、
**AskUserQuestion で 1 回にまとめて聞く。** ブランチ・コンテナの起動・ログインロール・
対象データの ID がここで揃う。

```sh
cat test/<領域>/<機能>/_background.feature
git -C repos/<リポジトリ名>/repo rev-parse --short HEAD
git -C repos/<リポジトリ名>/.worktrees/<ブランチ>/ rev-parse --abbrev-ref HEAD
```

動作確認は `repos/<リポジトリ名>/.worktrees/` の worktree で行う
(`repo/` は参照用で checkout を切り替えない)。
**どの worktree で見ているかを結果に書く**ので、ここで確定させる。

**揃っていないものがあればそこで止める。** 前提が崩れた状態で回した結果は使えない
(「この章は修正が入っていないブランチでないと成立しない」のような前提が実際にありうる)。

`@destructive` の章が含まれる場合は、**何が変わるかを先に伝えて確認を取る。**
ログインユーザーの権限、他の行、論理削除が対象になる。

### 3. シナリオを 1 つずつ回す

シナリオごとに `Given` / `When` を**通し番号つきでそのまま提示する。**
言い換えない — 番号は「U-2-3 の (5) で NG」と指すためのものなので、崩すと使えなくなる。
SQL は `sh` か `sql` のフェンスで貼り、そのままコピーできる形にする。

そのうえで `Then` を判定の選択肢にする。

| `Then` の数 | 聞き方 |
| --- | --- |
| 4 つ以下 | **multiSelect で各 `Then` を選択肢にする。** 選ばれなかったものが NG |
| 5 つ以上 | まず「すべて期待どおり / 一部が違う / 確認できない」の3択。「一部が違う」なら次の質問でどれが違ったかを絞る |

* 選択肢のラベルは `Then` の要点を短く、`description` に `Then` の全文を入れる
* **どの場合も「確認できない」を選択肢に入れる。** モックの制約や環境の都合で
  到達できないシナリオが実際にあり、それは NG ではない
* **NG のときだけ**「何が起きたか」を追加で聞く。OK は選ばせるだけで先に進む

**同じ `Given` を共有し、画面を見るだけのシナリオは 1 回の AskUserQuestion に
最大 4 問まとめてよい。** 状態を変えるシナリオは 1 問ずつにする
(前のシナリオの結果が次の前提になるため)。

`@manual` タグのシナリオもこのスキルでは普通に回す
(自動化できないだけで、人がやるなら問題ない)。

### 4. 後片付けを回す

**ここは飛ばさない。** テスト中の操作で行が論理削除されたり重複行が自動生成されたりして、
復元に手間が掛かるのが典型的な事故。

その回で流した `UPDATE` と、画面から行った操作を「環境の復元」表にまとめ、
**1 件ずつ戻したかを確認する。**

| 対象 | 変更内容 | 復元 |
| --- | --- | --- |
| `users` id=12 | `role` member → admin | 初期値に戻したか |

**復元先は「手順書に書かれた初期値」ではなく、実行前の実際の値。**
手順書の初期値は書かれた当時のものなので、`Given` を流す前に現在値を控えておく。

後片付けのシナリオ (`04-teardown.feature` のような) が手順書にあればそれを使う。
無ければ、その回の `Given` から機械的に組み立てる。

### 5. 結果を書く

`assets/<タスク名>/<実行日>/result.md` を作る。同じ日に2回目を回す場合は
`<実行日>-2/` のように連番を足す (上書きしない)。

```sh
J="job/<案件名>/task"
mkdir -p "$J/assets/<タスク名>/$(date +%F)"
```

書式は「[出力フォーマット](#出力フォーマット)」を参照。あわせてタスク md を直す。

| 選択 | 完了条件 | result.md |
| --- | --- | --- |
| 期待どおり | `[x]` | OK |
| 違った | `[ ]` のまま | **NG** + 何が起きたか |
| 確認できない | `[-]` | 確認不能 + 理由 |

タスク md に書くのは次の3つだけ。

* `## 完了条件` のチェックを `[x]` / `[ ]` / `[-]` に書き換える
* `## 参照先` の表に `../assets/<タスク名>/<実行日>/result.md` を日付つきで足す
* `## 結果` に結論を書く (全部 OK なら1行、NG があれば何が残っているか)

**実行の過程はタスク md に書かない。** 何をどの順で試したかは
`daily/<YYYY-MM>/<DD>/agents/<ツール名>/<セッションID>/` に置き、
タスクからは `## 参照先` でたどれる状態にする (このリポジトリの原則)。

```sh
S="$(./daily/create_session.sh)"
cp daily/template/_.md "$S/<タスク名>-verify.md"
```

最後に 1:1 対応を検証する。

```sh
./.claude/skills/verify-task/check_scenario_ids.sh job/<案件名>/task/list/<タスク名>.md
```

### 6. 次の一手を出す

* **NG があれば実装タスクへの差し戻しを提案する。** リンクの `mv` は
  task-transition エージェントに任せる (このスキルではやらない)
* 「確認できない」が出たら、**理由を手順書側に書き戻すかを聞く。**
  同じことを次回また試すのは無駄なので、`#` コメントで残す価値がある
  (書き戻し自体は人の判断を待つ)
* **踏んだ罠は `job/<案件名>/STORAGE.md` に追記する。** 「この画面はリロードしないと
  値が反映されない」のような知見は、次の実行でも同じ時間を溶かす
* タスクを `done` にするなら、結論1行も `STORAGE.md` に追記する
  ([CLAUDE.md](../../../CLAUDE.md) の「作業の進め方」)

## 中断する条件

以下に当たったら、その場で止めて状況を報告する。

* 前提 (ブランチ・コンテナ・ログイン・対象データ) が揃っていない
* `test:` の指すパスが存在しない、または feature が 1 つも無い
* 手順書の記述と画面が食い違っていて、どちらが正しいか判断できない
  (**手順書が古い可能性があるので、勝手に読み替えない**)
* 後片付けで元に戻せないものが出た

## 出力フォーマット

`result.md`。

```markdown

| ID | 結果 | 備考 |
| --- | --- | --- |
| U-1-1 | OK | |
| U-1-2 | OK | |
| U-1-3 | **NG** | (4) 押下できない。非活性のまま |
| U-1-4 | 確認不能 | 画面幅が足りずツールバー右端が見えない |

| --- | --- | --- |
```
