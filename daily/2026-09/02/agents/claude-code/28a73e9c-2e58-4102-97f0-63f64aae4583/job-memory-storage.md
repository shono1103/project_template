# 調査 — job 層の MEMORY / STORAGE 導入

## 目的

task / job ごとのスコープを持つメモリと、それを次の案件で使えるアーカイブを
このリポジトリの運用に組み込む。紐づく task は無い (このリポジトリ自体の構成変更)。

## 対象

README.md / CLAUDE.md / .claude/skills/reload-project/SKILL.md /
job/template/ / daily/README.md / docs/README.md

## 経過

### 既存の置き場を洗い出した

過程=daily / 結論=task / 継続参照=docs / 状態ダイジェスト=ルート MEMORY.md で切れている。
これに対して置き場が無いものが3つあった。

1. 案件固有の前提 (環境・URL・命名規則・慣習) — docs/ は「他人が読むドキュメント」で役割が違う
2. task の再開点 — 複数セッションにまたがると daily を N ファイル読む必要がある
3. ルート MEMORY.md の 1,500 トークン圧縮で落ちた情報 — 圧縮ルールは「削る」だけで行き先が無い

### MEMORY と STORAGE の役割分担を確認した

ユーザー確認の結果: MEMORY = 上限つきダイジェスト (再生成・圧縮される) /
STORAGE = 追記型アーカイブ (上限なし)。**圧縮は削除ではなく MEMORY → STORAGE への移動**。
上の 3 の欠陥がこれで埋まる。

### 層を job だけに絞った

* task 層の STORAGE は daily と役割が重複する (daily がすでに追記型・時系列・上限なし) → 不要
* 実データがゼロの段階で4種類のファイルを入れると書き分けの判断が増える

→ ユーザー確認の結果、**job 層のみ**から始めることにした。task 層は必要になってから。

### 案件をまたぐ再利用の方式を決めた

当初案は「job 完了時に汎化した知見をルート層へ昇格」。
ユーザーの選択は**探索方式** (似た案件を自律的に探すスキルを作る)。
昇格の規律に頼らない代わりに、**探索される前提で書く**必要が出る。
そこで job MEMORY.md に `## 属性` (種別 / 技術スタック / ドメイン / 関連リポジトリ /
キーワード) を検索キーとして持たせた。ここが埋まっていないと方式全体が機能しない。

### 上限値を実測で決め直した

最初 800 トークンにしたが、テンプレートの注記だけで 552 トークンあり中身が 250 しか入らない。
注記を削って 370 トークンにし、上限を 1,000 (警告 800) に変更した。
STORAGE.md は 264 トークン、find-precedent の SKILL.md は約 2,000 トークン。

### 仮の案件2件で通しの動作確認をした

`job/_smoke-old` (過去案件) と `job/_smoke-new` (現在の案件) をテンプレートから作り、
find-precedent の手順1〜4 のコマンドを実行した。**バグが1件出た**。

* 症状: `job/template/MEMORY.md` が先例としてヒットする
* 原因: テンプレートの注記に例として `Laravel, MySQL, Vue, AWS` `EC, 予約, 認証` と
  実際の技術名が書かれているため、属性の grep に必ず引っかかる
* 対処: `find ... -not -path 'job/template/*'` でファイル一覧を作ってから grep する形に変更。
  `grep --exclude-dir=template` は macOS (BSD grep) だとコマンドラインで渡した
  ディレクトリに効かないため使わない
* 再実行して template が除外されることを確認した

あわせて `sed -n '/^## 踏んだ罠/,/^## 畳んだ/p'` が「完了した task」節まで巻き込んでいたのを
`/^## 完了した task/` 止めに修正した。

### daily 記録の作成で shell に躓いた

`python3 - <<PY` (クォート無しの heredoc) で本文を流し込もうとしたところ、本文中の
バックティックがシェルのコマンド置換として解釈され、タイムアウトした。
ファイルへの被害は無し (`git status` で確認)。`<<'EOF'` に変更して解決。

## 分かったこと

* 既存の圧縮ルール (ルート MEMORY.md) は情報の行き先が無い片道の削除だった。
  MEMORY / STORAGE の対を入れると「畳む」に変わる。
* **自動生成と手書きの線引きが層の分担そのもの**になる。
  構成からスキャンで導出できるもの (task の状態) はルートが自動生成し、
  導出できない知識 (案件固有の前提と決定) は案件側が手書きする。
  そのため `/reload-project` は job 層を**読むが上書きしない**。
* 副作用として、ルート MEMORY.md は案件の詳細を持たず
  「詳細は `job/<案件名>/MEMORY.md`」と書けるので 1,500 トークンの圧迫が下がる。
  圧縮ルールの1番目にこれを入れた。
* 探索方式は昇格方式より書き手の負担が小さいが、**検索キーの記入が前提条件**になる。
  属性が空の案件は探索から漏れる。ここが方式の弱点。
* テンプレートに具体的な例を注記として書くと、そのテンプレート自身が検索にヒットする。
  探索系のスキルを書くときは複製元の除外を最初から入れる。

## 未解決

* task 層の MEMORY (再開点) は今回入れていない。task が複数セッションにまたがるように
  なってから `job/<案件名>/task/memory/<タスク名>.md` として足す想定
  (`list/todo/progress/done` と同階層なので相対シンボリックリンク方式に影響しない)。
* 属性の記入漏れを検出する仕組みが無い。`/list-task` か `/reload-project` で
  「属性が空の案件」を警告する余地がある。
* `job/<案件名>/STORAGE.md` が案件終了後にどれだけ育つか未知。
  実データが溜まってから、探索が実用的な速度で回るかを再確認する必要がある。
